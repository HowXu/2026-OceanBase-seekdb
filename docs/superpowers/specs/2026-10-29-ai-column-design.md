## 2. 方案取舍与现有接入点

### 方案 A：内核事务任务表 + 后台执行器（采用）

业务事务同时维护业务行、隐藏状态与持久化任务。后台只读取已提交任务，在短事务中领取，在事务外调用模型，然后在短事务中校验并发布。任务状态和待发布结果可恢复，不依赖进程内队列保证正确性。

### 方案 B：直接扩展混合向量后台任务（不采用）

已有向量任务机制可以借鉴线程生命周期、事务和资源释放方式，但它面向向量索引刷新，不直接提供文本列、条件重试或同行多 AI 列发布的语义。将这些功能塞入现有向量任务会扩大对原有索引功能的影响。

### 方案 C：事务提交回调 + 内存队列（不采用）

提交回调可以作为唤醒优化，但不能是任务唯一来源。提交完成到入队之间的崩溃、服务停止和执行中断都会产生丢任务风险，不符合持久化恢复要求。

### 已检查的现有机制

- 后台参考：`src/observer/vector_index/ob_hybrid_vector_refresh_task.h`、`ob_vector_index_async_task_scheduler.cpp`。只参考适用机制，不改变其既有业务语义。

## 3. 数据模型与元数据

### AI 列定义

`oceanbase.__all_ai_column` 持久化列名、表和列标识、原始及规范化表达式、依赖列 ID、异步配置、最大重试次数和定义版本，以及三个隐藏列的 ID：

- `state_column_id`：PENDING、READY 或 FAILED。
- `request_column_id`：当前列请求标识，用于结果归属校验。
- `result_spec_column_id`：行上对应的结果规格/定义校验信息。

AI 结果列是普通可见的物理结果列，不是每次查询都调用模型的虚拟生成列。隐藏列不暴露在普通 `SELECT *` 中，也不允许业务 SQL 绕过保护写入。元数据需要支持深拷贝、序列化、反序列化和列 ID 重映射；定义展示须保留 AI 语法及配置。

结果状态不能从结果是否 NULL 推断。默认模式中，PENDING 和 FAILED 的结果均为 SQL NULL；READY 状态与结果值是否 NULL 独立。

### 持久化任务

`oceanbase.__all_ai_column_task` 为每个待生成 AI 列保存一条任务，同一行同次变更触发的列共享 `request_id`。至少承载：

- 表、列及定义版本，结构化行键及可供诊断的 `rowkey_predicate`。
- 请求标识及请求组、绑定该次变更的模型输入和配置。
- 任务执行状态、`retry_count`、`eligible_ts`、领取归属、领取版本和租约截止时间。
- 已完成但尚未分组发布的结果或终态失败信息。

官方 DML 用例要求任务在业务事务内可见、`eligible_ts <= now(6)`，并检查简单 BIGINT 主键的展示形式为 `` `id` = 2 ``。展示文本不能代替安全的结构化行键校验。标识符及字符串必须使用现有引用/编码机制，不拼接未转义的业务值。

请求标识必须跨服务重启和同主键重插保持不复用，不能用时间戳精度或进程内递增计数代替唯一性保证。

## 4. DDL 与类型约束

支持题目要求的 `CREATE TABLE`、`ALTER TABLE ADD/MODIFY`、定义查看和 `SHOW AI COLUMNS`。解析、Schema 持久化和展示必须形成完整闭环，而不是只接受新语法。

Resolver 校验：

1. 仅接受异步模式，配置名称、类型和取值合法，`max_retries` 是可表示的非负整数。
2. AI 调用函数、参数数量、模型类别和表达式类型相容；非 AI 部分使用受支持的原生 SQL 表达式。
3. 不允许引用其他 AI 列形成链式依赖，也不允许自身依赖或依赖不存在的列。
4. 向量维度由目标列约束；显式 AI_EMBED 维度不匹配时按官方要求报错 7600。省略函数维度时仍以列维度约束实际返回值。
5. 禁止业务 SQL 对结果列及内部维护列直接赋值。

为 AI_COMPLETE 的规范化表达式补充目标类型系统提示。JSON 提示包含官方 Mock 检查的 `Return exactly one valid JSON value`；整数提示包含 `base-10 integer`。提示必须来自目标 SQL 类型，不能根据模型名或输入特判。用户正文、表达式配置和占位符含义保持不变。

模型返回后执行独立的类型检查：JSON 必须完整合法；整数验证完整文本及范围；数值拒绝非法及非有限值；字符串验证目标字符集和长度；向量验证数量、维度及有限数值。不能依赖模型遵守提示，也不能通过宽松转换把坏结果发布为成功。

ADD 到有既存数据的表时，需要初始化隐藏状态并为既存行建立可恢复的生成工作；不能把无结果的旧行默认为 READY。MODIFY、DROP、TRUNCATE 和删除表时，旧任务不能继续按旧定义写回，相关元数据和任务需要清理。执行这些操作时沿用已有 DDL 锁和 Schema 可见性机制。

## 5. 业务事务中的 DML 联动

### 触发规则

- INSERT：为受影响行建立所有 AI 列任务。
- 依赖列更新：使受影响 AI 结果失效，生成新请求。
- 无关列更新：保留结果和状态，不生成模型请求。
- 主键更新：清理旧行键任务，按新行键使结果失效并重新生成。
- DELETE：与业务删除一起清理待执行任务；已在途请求的迟到结果也不得恢复该行。
- 批量写入及原生 SQL 的其他实际写入路径：沿用同一行级维护逻辑，不仅支持简单单行 VALUES。

同一次行变更涉及多个 AI 列时，新任务共享请求组。只失效受影响列，其他 READY 列保持不变。

### 原子性

业务数据更新、结果置 NULL、状态切换、请求标识替换、旧任务处理和新任务写入，必须属于同一个事务及语句原子性范围。事务能读取自己的任务；其他会话和后台不能读取未提交任务。

业务事务 ROLLBACK、语句失败及保存点回滚应同时恢复结果、状态、任务及索引。若任务维护失败，不得只提交业务行。

后台通知可以延后或丢失，持久化扫描仍能发现工作。不得为了减少写入延迟将必要的失效和任务写入移到提交之后。

## 6. 后台调度、恢复与分组发布

### 执行流程

```text
业务事务提交
  → 发现已提交且 eligible 的任务组
  → 短事务领取：记录归属、领取版本与租约
  → 事务外执行模型调用
  → 持久化单列结果 / 重试信息 / 终态失败
  → 组内所有有效成员达到终态
  → 短事务校验并原子发布结果、状态、清理任务
```

执行器具有有界并发和有界批次。线程停止时停止领取，等待或取消在途工作并释放连接、请求和内存；未完成持久化任务可由后续执行器恢复。并发领取同一组只能有一个有效持有者；租约到期后的旧执行器即便返回也失去写入权限。

模型调用不得持有业务行锁、未结束的任务领取事务或 Schema 临时对象裸指针。表达式、输入、endpoint 和返回值必须有覆盖调用生命周期的所有权。

### 自动重试

`max_retries` 表示首次尝试之外允许的重试次数，最多执行 `1 + max_retries` 次任务级尝试。每次失败提交 `retry_count` 和下一次 `eligible_ts`，不能在持有事务时 sleep。官方 worker 用例要求首次失败后可观察到 `state = 3 AND retry_count = 1`，随后最终成功恰好两次请求。

HTTP 400 的官方故障注入也在任务级重试范围内，不能只重试 429/5xx。响应、转换或网络失败不得被记录为 READY；达到上限后进入 FAILED。重试延迟使用有界退避，避免占满线程及紧密重复请求。

外部服务“已执行但响应丢失”无法仅靠本地事务保证推理恰好一次。本实现保证任务归属和结果发布正确，允许恢复时再次推理，并在故障评测中如实统计实际调用次数，不假称避免了所有重复推理。

### 分组终态与旧结果保护

成功列的结果先暂存在任务中，不能提前写入业务结果列；失败重试中的同组其他列仍保持 PENDING。所有有效成员终态后，一个事务发布成功列为 READY、最终失败列为 FAILED，并删除组任务，允许同组成功与失败混合。

发布前重新校验：行存在、当前列请求标识、定义版本、任务归属和领取版本。受并发更新取代的列不得被旧请求写回；不能仅检查主键存在或正文相等。删除后同主键重插由新请求标识区分。

连续更新可能只影响部分 AI 列。取代旧组成员时必须同步维护该组成员关系；未被取代的列仍需完成，不能因为其他列换了请求就丢弃其计算，也不能让旧组等待一个已删除成员而永久卡住。

服务在单列结果落盘后、分组发布前中断时，恢复后复用已落盘终态，不必重做已完成计算。发布事务中断则整体回滚或整体提交，不产生部分结果可见。

## 7. 条件重试与严格读取

### 条件 RETRY

支持 `ALTER TABLE t RETRY AI COLUMN c [WHERE predicate]`，只针对一个 AI 列，不得与其他 ALTER 动作混用。目标不是 AI 列或混用其他动作时按官方要求报错 1235。

条件使用原生 SQL 表达式求值，不通过字符串替换实现：

- 未加反引号的 `status` 是目标 AI 列状态伪列，可匹配 PENDING、READY、FAILED，并与业务字段条件组合。
- 反引号引用的 `status` 是同名业务列。
- 无 WHERE 作用于全部行，零行匹配是无副作用操作。
- READY 行允许重新生成；未选中的行和其他 AI 列保持不变。

选中行的失效、旧任务处理和新任务创建以事务方式完成；该入口是结果保护的受控内核操作，不开放给普通 SQL 绕过赋值限制。

### 严格读取

`ai_column_strict_read` 是默认 OFF 的会话变量。ON 时，语句实际引用的每个 AI 列在其所属表内存在任何非 READY 行即报错 11120，并提供表、列标识。

检查范围包含投影、过滤、排序、表达式、连接和子查询中的引用，以及 UPDATE/DELETE 的读取表达式；只访问普通列或完全 READY 的其他 AI 列不受影响。列级检查不能因 WHERE、LIMIT、空结果或优化器列裁剪被绕过。

在执行阶段、首次业务写入及结果返回之前检查，并与语句读取使用一致的快照语义。缓存计划执行时读取当前会话变量，不能仅在 Resolver 阶段判断一次。内部任务维护和结果发布使用不可由用户伪造的受控执行上下文，避免严格读取阻塞自身生成。

本阶段不引入并发敏感的“未就绪行计数缓存”代替正确性检查；若采用任何优化，必须先证明它与事务、快照和回滚一致。

## 8. 向量与索引维护

向量结果是原生物理 VECTOR 列。失效时将结果更新为 NULL，发布时更新为新向量，两者均通过原生事务和索引维护链路完成，不能只更改查询显示值或在后台绕过 DML 直接修改行存储。

HNSW/VSAG 索引应遵守同一事务可见性：依赖更新后当前事务的 ANN 不再返回旧向量；提交后新向量可以参与检索；回滚恢复原向量、任务和 ANN 可见性。删除及主键更新同样不得遗留可见旧索引项。

索引正确性要检查查询结果及 EXPLAIN 路径，不以普通全表排序的正确结果冒充使用向量索引通过。
