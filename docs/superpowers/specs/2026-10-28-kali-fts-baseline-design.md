# Kali 编译适配与 FTS 初步优化分析设计

## 目标与边界

在当前 `2026-competition-fts` 分支合入提交 `1032025add14d5acbe836a6c31c77942ba438dac`，适配本地 Kali 开发环境并完成实际编译。随后理解赛题及计分方法，解释初步优化的瓶颈，探索后续优化方向。

本阶段不合并整个 `kernel/2026-competition` 分支，不在环境适配中混入性能优化，不将不同编译配置或机器的数据直接作为优化前后对比。

## 提交集成

完整 cherry-pick 指定提交，保留其 Kali 依赖选择、`run_temp/` 忽略规则及已有测试脚本。合入前确认工作区干净；若冲突，仅解决当前分支与指定提交之间的冲突。测试脚本不得执行任何外部上报。

验证：`git status` 显示预期改动，`git log` 能找到该提交的合入记录，并核对合入后的补丁范围。

## 编译适配

优先复用已有 `build_release/` 的 `RelWithDebInfo` 配置，按项目构建文档运行编译。发生错误时保留首个有效错误及上下文，检查工具链、依赖和分支代码差异；每次只针对已定位的原因做最小修改。

验证：
1. 编译命令成功退出，目标二进制存在。
2. 对适配涉及的代码运行可行的针对性测试；若某项因环境无法运行，明确记录命令和阻塞原因。
3. `git diff --check` 通过；最终差异仅包含环境适配及其必要修复。

## 赛题与初步优化分析

阅读赛题页面、仓库内 `tools/benchmark/fts_large_bench.sh` 及其基准配置，确认测试数据、指标定义、得分公式、正确性约束和测试环境。核对 `fts_mean_improvement = -0.0557631546667764` 的实际含义，不先验认定整体性能下降 5.58%。

检查当前分支相对上游竞赛基线的 FTS 改动，将优化按 IK 字符处理、分词仲裁、文档 ID 比较及 posting-list 合并分组。从现有结果区分已测事实、推断和待验证假设；仅凭汇总时间不把某项认定为热点。

## 后续优化探索

在同一机器、同一构建配置和相同数据下建立可复现的 A/B 基线。按构建、分词、查询分别收集计时；需要时用 profiler 定位热点，并结合正确性结果评估候选优化。

优先考虑减少重复解码与内存分配、降低分词器调用及仲裁开销、改善短 posting-list 合并与比较的数据访问；具体方案必须依据调用链和测量结果选择。每项候选给出预期收益、正确性风险、验证方法，先报告分析结论，再选择单项实施。

验证：基准结果无正确性回退；重复测量确认收益超过波动；报告原始数据、比较条件和未验证的限制。
