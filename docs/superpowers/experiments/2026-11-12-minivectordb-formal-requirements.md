## 1. 原拒绝检查（其中两种格式的非法分类已撤回）

测试表为 VECTOR(2)。非法输入包括：

- NaN/nan、Infinity/-Infinity/Inf。
- 正负 float32 溢出 `1e39`、`-1e39`，以及更大指数 `1e309`、`-1e309`。
- 空数组、维度少一个、多一个。
- null、字符串数字、bool 元素。
- 尾逗号、非法前导零、前导正号、缺分隔符、尾随垃圾、不完整指数。

对全部 21 个输入分别执行：

1. 多行 INSERT，第一行有效、第二行非法，检查有效前缀也不能生效。
2. 对多条匹配记录执行 UPDATE。
3. 非空集合的 exact 距离排序查询。
4. 非空集合的 ann 距离排序查询。
5. 空集合加 LIMIT 0，确认没有跳过表达式绑定/向量验证。

105 项均返回非空 `type_error`，之后完整标量/向量表状态与独立基线一致，进程继续可用。

另测最大有限 float32、最小正 subnormal、负零；读取向量投影后按 `struct.pack('<f', value)` 比较位模式，不仅检查“是个有限数”。最大有限正负向量间的距离也为有限 double。没有将未明确冻结的极小值舍入到零策略擅自列为本轮缺陷修复目标。

源码核对：`types.cpp::parse_vector` 在词法、维度、from_chars 转换状态和 finite 检查处拒绝非法值；INSERT/UPDATE 经 bind_literal，L2_DISTANCE 查询也使用该解析器。

## 2. 失败语句之后必须仍可提交或回滚

### 继续提交

- BEGIN 后先成功插入记录，并成功更新第二张表。
- 依次制造多行主键冲突、多行非法向量、多行超长 VARCHAR、非法向量 UPDATE。
- 每次失败后核对完整第一张表和第二张表，之前成功记录仍在，失败语句的新记录前缀均不存在。
- COMMIT 收到成功响应后实际 Docker KILL，重启核对两表和向量结果，成功修改保留。

### 继续回滚

- 在新事务中成功更新向量/普通列、删除记录、更新第二张表。
- 制造一次有效前缀加已有主键冲突的多行 INSERT。
- 失败后此前成功删除仍在当前事务内可见，随后 ROLLBACK。
- 完整表内容、记录集合、第二张表及向量检索恢复到已提交状态。

另外，在 24 个 ANN 状态中再次检查失败语句后普通全表与向量结果均对应当前事务；事务内创建的索引在回滚后名称可以重新使用，检查了索引定义的事务回滚。

源码核对：`engine.cpp::execute` 使用 statement_candidate，成功后才替换事务根或发布；失败不会直接覆盖可见根。此处同时以实际状态检查佐证，不只依赖源码推断。

## 3. 强杀、提交确认与重复恢复

本轮没有用终止 Docker CLI 代替数据库崩溃，调用的是实际 `docker kill --signal=KILL <container>`。

- COMMIT 成功响应已经读取后强杀：两表普通数据及向量保留。
- BEGIN 后修改两表，但从未发送 COMMIT 请求便强杀：两表和向量均恢复旧状态。
- 三个 ANN 数据集分别执行已确认提交后强杀、未提交变更后强杀；恢复后的全量行状态与独立模型一致。
- 2,112 MiB 数据复用同一卷恢复：再次启动时，用只读诊断观察 `/proc/1/fd` 已打开 `/data/objects/*.tbl`，且 stdout 尚未输出 ready，然后 KILL。再启动成功，全部主键、内容样本及向量结果正确。

大数据两次成功恢复到 ready 的端到端时间分别约 1,329ms、1,241ms。中间被终止的启动没有输出 ready。观察 FD 的临时诊断进程不是数据库接口，没有修改文件或开启生产故障注入。

本轮重点验证 README 列出的确认提交/未提交/重复恢复。此前对“发送提交后未读取响应”的不确定确认窗口已有单独小数据证据；本轮不将有限实验扩张为全部内部发布切点的穷举验证，也没有模拟断电或磁盘损坏。

## 5. ANN 必须用独立真值，而不是只看 mode 被接受

### 数据和真值

- 固定种子 17、911、20261111，分别为 8、16、128 维，每组初始 128 行。
- 主键非连续；包含明确距离并列的记录，检查 PK 规则。
- 宿主端使用标准库 struct 将输入与查询量化为 float32，再用 math.fsum 独立计算欧氏距离，按距离、PK 排真值。
- 查询覆盖零向量、接近某条记录的向量、随机查询向量；无过滤、两类过滤、空过滤集合；K=1/10/200，含 K>N。
- 预期状态只由生成输入、成功操作和事务规则推导，不以数据库返回值作为答案。

### 每个种子核验八个状态

1. 未建索引。
2. 建索引后。
3. 事务内更新向量和过滤字段、删除、插入及创建索引后。
4. 同一事务内一条多行语句失败后。
5. ROLLBACK 后，含索引名称重新使用。
6. COMMIT 后。
7. 已确认 COMMIT 后强杀并恢复。
8. 新事务修改、未发送 COMMIT 就强杀并恢复。

共 24 个状态，每个状态都先比较完整普通行/向量存储结果，再验证 exact 与 ann。

每次查询检查数量、有效 ID、无重复、满足 WHERE、对应当前记录的距离、有限输出、距离和 PK 排序。exact 须匹配精确真值；ann 计算实际 Recall。空集合必须为空，不进入均值；每个状态分别检查有/无过滤的平均 Recall 不低于公开赛题 §3.3 给出的 0.95 目标，不将坏状态稀释到其他状态的均值中。README 未单独给出正式 ANN 用例的数值阈值，本轮不把性能章节的阈值冒称为已经取得的隐藏用例配置；实际所测每条非空查询 Recall 均为 1.0。

### 实测结果

| 模式/分组 | 非空查询数 | 平均 Recall | 最低单查询 Recall |
|---|---:|---:|---:|
| exact 无过滤 | 216 | 1.0 | 1.0 |
| exact 有过滤 | 432 | 1.0 | 1.0 |
| ann 无过滤 | 216 | 1.0 | 1.0 |
| ann 有过滤 | 432 | 1.0 | 1.0 |

合计 **1,728 次查询**，其中 exact 864 次、ann 864 次。**这 1,728 次中有 432 次为空集合检查**（每种模式 216 次），已计入查询总数，但不进入上述 Recall 均值。

单独提取 K=10 的 ANN 查询：无过滤 72 次、有过滤 144 次，平均及最低 Recall@10 均为 1.0，见 `recall-at10-summary.json`。

现实现 ann 使用 FlatScan exact fallback，达到这些正确性结果不等于实现了 HNSW/近似加速。README 这条要求的过滤、有效 ID、无重复、Recall 和索引事务可见性在所测状态中通过；没有取得或伪造正式隐藏随机种子和冻结性能结果。
